# Critique Report: Agenda (Gestao de Agendamentos)

**Date**: 2026-05-23
**Feature**: specs/agenda/
**Status**: migrated (existing codebase)
**Reviewer**: speckit-critique-run (dual-lens)

---

## Executive Summary

The Agenda module is a well-scoped, functional appointment management system with a strong frontend Clean Architecture implementation. The backend is pragmatic CRUD rather than full CA, creating an architectural asymmetry. Two 🎯 Must-Address items relate to stale gap documentation and missing operational safeguards. Overall readiness: **PROCEED WITH UPDATES**.

---

## Product Lens Findings

### Problem Validation (3a)
- **Finding**: Problem is clear and well-defined — dental clinic appointment scheduling is a core operational need.
- **Assessment**: ✅ Valid. No solution-looking-for-problem risk.

### User Value Assessment (3b)
- **Finding P1**: US1-US6 cover the full user journey from creation to confirmation to blocking. US7 (reminders) is P2 but lacks backend implementation detail — no actual reminder-sending service is documented.
- **Suggestion**: Clarify whether reminder sending is implemented (SMS gateway, push notification provider) or stubbed. If stubbed, downgrade US7 to P3 or create a follow-up feature spec.

### Alternative Approaches (3c)
- **Finding P2**: The module implements both Calendar and List views. Could a single view with toggle suffice? The current dual-view adds maintenance surface.
- **Suggestion**: Consider deprecating List view if Calendar view gains list-mode capability, reducing UI complexity.

### Edge Cases & UX (3d)
- **Finding P3**: Missing edge case: what happens when a dentist is deactivated/deleted but has future appointments?
- **Suggestion**: Add business rule for dentist deactivation — either block deletion with future appointments or auto-cancel with notification.
- **Finding P4**: Missing edge case: recurring appointments (weekly checkups) are not supported.
- **Suggestion**: Document as out-of-scope or add to backlog.

### Success Measurement (3e)
- **Finding P5**: Success criteria are mostly measurable. "Lembretes são enviados e registrados com sucesso" depends on an external notification provider not defined in the spec.
- **Suggestion**: Remove or qualify this criterion until reminder infrastructure is specified.

## Engineering Lens Findings

### Architecture Soundness (4a)
- **Finding E1**: Frontend uses Clean Architecture (Domain → Application → Infrastructure → Presentation → UI) with repository pattern and use cases. Backend uses Express CRUD with Prisma directly, with only partial CA adoption (domain entity + command exist but controller doesn't use them).
- **Suggestion**: Document this intentional asymmetry in the plan, or create a refactor task to align backend with frontend architecture.

### Failure Mode Analysis (4b)
- **Finding E2**: No retry strategy or circuit breaker for API calls. If the backend is temporarily unavailable, the frontend fails silently or shows generic error toasts.
- **Suggestion**: Add TanStack Query retry configuration (already available, just needs documentation).
- **Finding E3**: No rate limiting on `/api/agenda/*` endpoints. A malicious user could spam appointment creation.
- **Suggestion**: Add Express rate limiter to agenda router.

### Security & Privacy (4c)
- **Finding E4**: `clinicGuard` provides multi-tenant isolation. However, the `checkConflict` endpoint returns conflict count — could be used to enumerate other clinics' appointments if clinicGuard has a bypass vulnerability.
- **Suggestion**: Verify `checkConflict` strictly enforces `clinic_id` filter (it does in code, but document as security-sensitive).

### Performance & Scalability (4d)
- **Finding E5**: Calendar loads all appointments for the week without pagination. For clinics with 200+ appointments/day, this could be 1,400+ appointments per week.
- **Suggestion**: Add virtual scrolling to WeekCalendar or implement server-side pagination with lazy loading.
- **Finding E6**: `ListAppointmentsUseCase` loads all appointments into memory. No pagination in the list endpoint.
- **Suggestion**: Add pagination parameters to `GET /appointments`.

### Testing Strategy (4e)
- **Finding E7**: Good test pyramid — domain entity tests, use case tests, mapper tests, hook tests, E2E tests. Missing: backend integration tests for conflict detection and blocked time overlap.
- **Suggestion**: Add integration tests for `checkConflict` and blocked time logic.

### Operational Readiness (4f)
- **Finding E8**: No custom metrics or alerting for agenda operations.
- **Suggestion**: Add Prometheus metrics for appointment creation rate, conflict detection rate, cancellation rate.

### Dependencies & Integration (4g)
- **Finding E9**: Standard dependency stack (React, Express, Prisma, Zod). No risky third-party dependencies.
- **Assessment**: ✅ Low risk.
