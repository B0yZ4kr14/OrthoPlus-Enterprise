## 1. A01: Broken Access Control 🔴

### [CRITICAL] ~~A01-1: `getFile` and `downloadFile` bypass visibility ACL~~ ✅ FIXED
**File:** `backend/src/modules/files/api/filesController.ts`

**Issue:** While `listFiles` correctly filters by user role via `userRole`, both `getFile` and `downloadFile` only checked `clinic_id` isolation. They did NOT verify whether the requesting user's role was allowed to access the file's visibility level.

**Fix Applied (2026-05-18):**
- Added `enforceVisibilityAcl()` helper function
- Applied in both `getFile` (line ~137) and `downloadFile` (line ~195)
- PATIENT→PUBLICO only; MEMBER→no CONFIDENCIAL; ADMIN→no restriction

**Risk:** IDOR + Horizontal privilege escalation — **RESOLVED**

---

### [HIGH] ~~A01-2: `uploadFile` lacks role-based restrictions~~ ✅ FIXED
**File:** `backend/src/modules/files/api/filesController.ts`

**Issue:** Any authenticated user (including PATIENT) could upload files and set any visibility level including CONFIDENCIAL.

**Fix Applied (2026-05-18):**
- Added `sanitizeUploadVisibility()` helper function
- PATIENT forced to PUBLICO regardless of input
- MEMBER blocked from CONFIDENCIAL (falls back to RESTRITO)
- ADMIN allowed all visibility levels

**Risk:** Privilege escalation via upload — **RESOLVED**

## 2. A02: Security Misconfiguration 🟡

### [MEDIUM] A02-1: `upload-cloud` lacks clinic isolation check
**File:** `backend/src/modules/files/api/filesController.ts` (lines 294-361)

**Issue:** The `uploadBackupToCloud` function reads `backupId` from req.body and queries `prisma.backup_history.findUnique({ where: { id: backupId } })` without verifying `clinic_id` or user ownership.

**Impact:** Potential cross-clinic data access if backup IDs are guessable.

**Remediation:** Add `clinic_id` check:
```typescript
const backup = await prisma.backup_history.findFirst({
  where: { id: backupId, clinic_id: req.user?.clinicId }
});
```

## 3. A05: Injection 🟡

### [MEDIUM] A05-1: `path.join` with storage filename from DB
**File:** `backend/src/modules/files/api/filesController.ts` (lines 141, 199, 270)

**Issue:** `file.nomeStorage` is used directly in `path.join(uploadDir, file.nomeStorage)`. While `nomeStorage` is generated by multer with sanitization, if the DB record is tampered with (e.g., via direct SQL injection elsewhere or compromised admin), this could lead to path traversal.

**Impact:** Potential arbitrary file read if `nomeStorage` contains `../` sequences.

**Remediation:** Validate `nomeStorage` before use:
```typescript
if (file.nomeStorage.includes("..") || file.nomeStorage.includes("/")) {
  throw Errors.internal("Invalid file storage name");
}
```

## 4. A06: Insecure Design 🟡

### [HIGH] ~~A06-1: File deletion is non-atomic (DB vs filesystem)~~ ✅ FIXED
**File:** `backend/src/modules/files/api/filesController.ts`

**Issue:** The delete operation deleted the DB record first, then the file from disk. If disk deletion failed, the file remained as an orphan.

**Fix Applied (2026-05-18):**
- Reversed order: disk file removed first (`fs.unlinkSync`), then DB record deleted (`filesService.delete`)
- Prevents orphan files if DB deletion fails after disk deletion succeeds

**Risk:** Storage leak / compliance gap — **RESOLVED**

---

### [MEDIUM] A06-2: No virus scanning on upload
**File:** `backend/src/modules/files/api/router.ts` (multer config)

**Issue:** No virus/malware scanning on file uploads. The MIME type whitelist and file extension check are not sufficient to detect malicious content.

**Impact:** Malware could be uploaded and downloaded by clinic staff.

**Remediation:** Integrate ClamAV or cloud scanning (already deferred as SEC-006).

---

### [MEDIUM] A06-3: No file integrity verification
**File:** `backend/src/modules/files/api/filesController.ts`

**Issue:** No checksum (SHA-256/MD5) is computed or stored for uploaded files. Cannot detect tampering or corruption.

**Impact:** Silent file corruption or tampering goes undetected.

**Remediation:** Compute and store SHA-256 hash on upload; verify on download.

### [MEDIUM] A09-2: Audit log failures are silent
**File:** `backend/src/modules/files/api/filesController.ts` (lines 145-157, 207-219)

**Issue:** Audit log failures are caught with `.catch(() => {})` and only logged at warn level. In a security incident, missing audit logs could go unnoticed.

**Impact:** Audit log gaps not alerted; compliance requirements (LGPD) may be violated.

**Remediation:** Consider incrementing a metric counter on audit log failure for monitoring/alerting.

## 6. A10: Exception Handling 🟡

### [MEDIUM] A10-1: `getFile` returns `existsOnDisk` boolean which leaks filesystem state
**File:** `backend/src/modules/files/api/filesController.ts` (lines 159-166)

**Issue:** The API response includes `existsOnDisk: exists`, which reveals whether the file exists on the server's filesystem. This information could aid an attacker in probing the filesystem.

**Impact:** Information disclosure.

**Remediation:** Remove `existsOnDisk` from API response or only include it for ADMIN role.

---

### [MEDIUM] A10-2: Error metric may use wrong clinic ID
**File:** `backend/src/modules/files/api/filesController.ts` (lines 76, 233, 282)

**Issue:** Error metrics use `(req.user?.clinicId as string) ?? "unknown"`. If authentication fails or `req.user` is not set, all errors are bucketed under "unknown", reducing metric usefulness.

**Impact:** Reduced observability during auth failures.

**Remediation:** Use `clinicId` from local scope (already validated) instead of `req.user?.clinicId`.
