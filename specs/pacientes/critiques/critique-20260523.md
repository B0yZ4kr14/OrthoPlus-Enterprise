# Critique Report: Pacientes (Gestao de Pacientes)

**Date**: 2026-05-23
**Feature**: specs/pacientes/
**Status**: migrated (existing codebase)
**Reviewer**: speckit-critique-run (dual-lens)

---

## Executive Summary

The Pacientes module is a comprehensive patient management system with an excellent backend CQRS architecture and a rich multi-tab clinical form. However, it suffers from a critical security violation (SEC-2.4), frontend architectural mismatch with the Agenda module, and several incomplete user stories. Overall readiness: **🛑 RETHINK** — security and spec gaps must be resolved before extension.

---

## Product Lens Findings

### Problem Validation (3a)
- **Finding**: Problem is clear — patient registration and clinical record management is fundamental to any dental practice management system.
- **Assessment**: ✅ Valid.

### User Value Assessment (3b)
- **Finding P1**: US1 and US2 have full acceptance scenarios. US3-US6 only have titles/context without GIVEN/WHEN/THEN scenarios, making them untestable and ambiguous.
- **Suggestion**: Add acceptance scenarios to US3 (search/filter), US4 (timeline), US5 (status change), and US6 (portal auth).

### Alternative Approaches (3c)
- **Finding P2**: The 7-tab patient form is comprehensive but may overwhelm users. A progressive disclosure pattern (basic info first, advanced tabs on demand) could improve UX.
- **Suggestion**: Consider defaulting to a collapsed state for Medical History, Habits, and Marketing tabs.

### Edge Cases & UX (3d)
- **Finding P3**: No documented handling for duplicate CPF across different clinics (multi-tenant edge case). The deduplication logic likely scopes by clinic_id, but this isn't explicit in the spec.
- **Suggestion**: Clarify in FR1.4 that deduplication is clinic-scoped.
- **Finding P4**: Patient portal auth (US6) has no password reset or account recovery flow.
- **Suggestion**: Document as out-of-scope or add recovery flow to backlog.

### Success Measurement (3e)
- **Finding P5**: "Busca retorna resultados em < 500ms para base de 10k pacientes" is measurable but not validated. No load testing task exists.
- **Suggestion**: Add a performance benchmark task or downgrade to aspiration rather than criterion.

## Engineering Lens Findings

### Architecture Soundness (4a)
- **Finding E1**: Backend uses CQRS (commands/queries separation) with domain events, value objects, and repository pattern — excellent. Frontend uses direct `apiClient` calls instead of use cases, diverging from the Agenda module's Clean Architecture pattern.
- **Suggestion**: Standardize frontend architecture across modules per EP-2, or document the divergence with justification.

### Failure Mode Analysis (4b)
- **Finding E2**: Patient timeline endpoint performs 4 parallel Prisma queries (appointments, treatments, budgets, status history). If one query fails, the entire endpoint fails with no partial result handling.
- **Suggestion**: Wrap each query in try/catch and return partial timeline with error indicators.
- **Finding E3**: No retry strategy for `apiClient` calls in the frontend.
- **Suggestion**: Document or configure axios retry policy.

### Security & Privacy (4c)
- **Finding E4** 🎯: `POST /api/pacientes/auth` returns token in JSON response body (`{ token: sessionId, ... }`). This violates SEC-2.4 (HttpOnly/Secure/SameSite=Strict cookies required).
- **Suggestion**: CRITICAL — Migrate patient portal auth to HttpOnly cookies before any portal deployment.
- **Finding E5**: Patient CPF and email are stored in plain text (no encryption at rest mentioned). LGPD compliance (NFR5) is claimed but not verified.
- **Suggestion**: Document encryption strategy for PII or add encryption-at-rest tasks.
- **Finding E6**: `dbRouter` exists in pacientes module with unclear access controls. Could expose database admin operations.
- **Suggestion**: Audit `dbRouter` routes and ensure they are admin-only or disabled in production.

### Performance & Scalability (4d)
- **Finding E7**: Full-text search (`PacienteSearchService`) likely performs `LIKE '%term%'` queries which don't scale linearly. For 10k+ patients, this will degrade.
- **Suggestion**: Add PostgreSQL full-text search index (GIN) or consider a dedicated search engine (Elasticsearch/Meilisearch) for patient search.
- **Finding E8**: Patient list page performs client-side filtering after loading all patients. For large clinics, this loads excessive data.
- **Suggestion**: Move search/filter to server-side with debounced API calls.

### Testing Strategy (4e)
- **Finding E9**: Only 1 unit test for the 473-line `Patient` entity. The entity has complex validation (CPF, email, status transitions, domain events) that is under-tested.
- **Suggestion**: Add tests for status transition edge cases, CPF validation edge cases, and domain event emission.
- **Finding E10**: E2E tests use text-based locators (`getByLabel`, `getByRole`) which are brittle. No `data-testid` strategy is documented.
- **Suggestion**: Add `data-testid` attributes to patient form fields and list items.

### Operational Readiness (4f)
- **Finding E11**: No custom metrics for patient operations (registration rate, search latency, portal login failures).
- **Suggestion**: Add Prometheus metrics for critical patient operations.

### Dependencies & Integration (4g)
- **Finding E12**: `bcrypt` is used for patient portal password hashing. This is a well-maintained dependency but the password hashing round count should be documented.
- **Suggestion**: Document bcrypt cost factor (e.g., 12 rounds) in the spec.

## Verdict

**🛑 RETHINK**

Must-address items before proceeding:
1. **CRITICAL**: Fix SEC-2.4 violation in patient portal auth (HttpOnly cookies)
2. **CRITICAL**: Document or implement PII encryption at rest (LGPD compliance)
3. **HIGH**: Add acceptance scenarios to US3-US6
4. **HIGH**: Address frontend architectural mismatch with Agenda module
5. **MEDIUM**: Add server-side search/filter and database indexing for patient search

After resolving must-address items, re-run `/speckit.critique.review` to verify readiness.
